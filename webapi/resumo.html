Resumo de prova

O cliente manda verbo + URL + cabeçalho (+ corpo). A API passa pelo Controller, pelo Service e pelo DbContext até o banco e devolve status + cabeçalho (+ corpo). A matéria inteira é esse caminho.
Formato da prova: 10 questões do professor (aulas e projeto Acervo) + 10 questões de concurso público de TI. Para as de concurso, cuidado com as palavras sempre, nunca, obrigatoriamente e apenas.

1. HTTP, cliente-servidor e API

  • Front-end: interface com o usuário, roda no navegador (HTML, CSS, JavaScript, Angular). Back-end: roda no servidor, processa a solicitação e retorna a resposta (C#, Java, Python, PHP).
  • API (Interface de Programação de Aplicações): regras e padrões que permitem a comunicação entre aplicações diferentes.
  • HTTP: protocolo de comunicação baseado em requisição e resposta. É a base da comunicação com a API.
  • O servidor tem endpoints, regras de negócio e acesso a dados.

2. WebServices, SOAP e REST

  • WebService: tecnologia de comunicação e troca de dados entre sistemas diferentes obrigatoriamente por meio de uma rede.
  • SOAP: modelo mais antigo, rígido e muito seguro. Usa XML (envelope SOAP), contrato descrito em WSDL.
  • REST: modelo mais novo, leve e rápido. Usa os verbos da web (HTTP) e os dados podem ser JSON ou outros formatos.
CaracterísticaAPIWebService
EscopoTermo genérico para qualquer interface de softwareSubconjunto de APIs focado em rede

DesignFlexível (DLLs, bibliotecas nativas, Web)Arquitetura cliente-servidor Web
AcessoSistemas internos ou externosQuase sempre via HTTP/HTTPS

REST: as restrições

Estilo arquitetural para sistemas distribuídos que usa HTTP. Quando a aplicação atende a todas as restrições, ela é RESTful.

Interface uniforme
Requisições para o mesmo recurso têm a mesma aparência, não importa a origem.
Desacoplamento cliente-servidor
Cliente e servidor evoluem de forma independente.
Stateless (sem estado)
Cada requisição traz tudo que é preciso para processá-la. O servidor não guarda sessão do cliente. (Por isso o JWT vai em toda requisição.)
Cache
Respostas podem ser armazenadas no cliente ou num intermediário.
Sistema em camadas
Pode haver intermediários (proxy, balanceador) entre cliente e servidor.
Código sob demanda (opcional)
O servidor pode enviar código executável ao cliente. É a única restrição opcional.

URLs REST: recurso no plural, verbo no método

GET    /api/alunos       lista todos
GET    /api/alunos/10    busca um
POST   /api/alunos       cria (sem id na URL: o banco gera)
PUT    /api/alunos/10    altera
DELETE /api/alunos/10    remove

Errado: GET /api/buscarAlunos · POST /api/alunos/10 · GET /api/alunos/excluir/10

Camadas da API

4. Persistência com ORM (Entity Framework Core)

Memória (List<T>)Banco de dados (tabelas)
Temporária: dados somem ao encerrarPersistente: dados permanecem
Boa para testes simplesAdequada para aplicações reais
Não compartilhada entre instânciasPode ser compartilhada
  • ORM (Object-Relational Mapping): facilita a comunicação entre o modelo orientado a objetos da aplicação e o modelo relacional do banco. Classe ↔ tabela, propriedade ↔ coluna, objeto ↔ linha.
  • EF Core: o ORM da disciplina. Fluxo: ASP.NET Core → EF Core → SGBD → banco.
  • Pacotes NuGet: Microsoft.EntityFrameworkCore.SqlServer (integração com SQL Server), .Design (recursos de desenvolvimento, inclusive migrations), .Tools (comandos das migrations).
  • DbContext: uma sessão de comunicação entre a aplicação e o banco. DbSet<Livro> Livros: representa o conjunto de livros (a tabela); é por ele que se opera nos registros.
  • String de conexão no appsettings.json (ConnectionStrings:DefaultConnection); registro no Program.cs com AddDbContext<AppDbContext>(o => o.UseSqlServer(...)).
  • Migration: uma evolução da estrutura do banco. Add-Migration CriarTabelaLivro cria a migração; Update-Database aplica no banco (no Console do Gerenciador de Pacotes).

CRUD com o contexto

await _context.Livros.ToListAsync();                 // lista
await _context.Livros.FindAsync(id);                  // busca pela chave primária
_context.Livros.Add(livro);                           // marca para inserir
_context.Livros.Remove(livro);                        // marca para excluir
await _context.SaveChangesAsync();                    // grava tudo no banco

Sem SaveChangesAsync() nada vai para o banco: o contexto só acompanha as mudanças.

    .WithMany(a => a.Livros)                 // um autor tem muitos livros

modelBuilder.Entity<Livro>()
    .HasMany(l => l.Categorias)
    .WithMany(c => c.Livros);                // N:N

Autor é a entidade principal; Livro é a dependente (tem a FK). Ao excluir um autor com livros, as opções são: excluir os livros junto (Cascade, o padrão do EF quando a FK é obrigatória), impedir a exclusão (Restrict) ou deixar o livro sem autor (SetNull, exige FK anulável).

5. Filtros e consultas

Filtros reduzem os dados trafegados, melhoram o desempenho e a experiência, tiram processamento do front-end e reaproveitam o mesmo endpoint.

var query = _context.Livros.AsQueryable();         // nada vai ao banco ainda

if (!string.IsNullOrWhiteSpace(filtro.Titulo))
    query = query.Where(l => l.Titulo.Contains(filtro.Titulo));   // busca parcial (LIKE)
if (filtro.AnoInicio.HasValue)
    query = query.Where(l => l.AnoPublicacao >= filtro.AnoInicio.Value);
if (filtro.Categoria.HasValue)
    query = query.Where(l => l.Categorias.Any(c => c.Id == filtro.Categoria.Value));

switch (filtro.OrdenarPor.ToLower()) { case "titulo": query = query.OrderBy(l => l.Titulo); break; ... }

return await query.Select(...).ToListAsync();      // aqui o SQL é montado e executado
  • DTO de filtro (LivroFilterDTO + [FromQuery]): evita assinaturas enormes conforme os filtros crescem. Propriedades com ? são opcionais.
  • Igualdade x parcial: l.Titulo == filtro.Titulo busca igual; l.Titulo.Contains(filtro.Titulo) busca parcial.
  • Any verifica existência (true/false). Count diz quantos atendem à condição. FirstOrDefault retorna o primeiro ou null.
  • Status de filtro: filtro sem resultado → 200 OK com lista vazia []. Recurso específico inexistente (/api/livros/999) → 404.

O front-end pode validar (melhora a UX), mas não há garantia: os dados podem vir direto do Insomnia. A validação no back-end protege a aplicação.

  2. ASP.NET Coredesserialização / model binding: transforma o JSON em objeto
  3. LivroCreateDTOData Annotations são verificadas
  4. Controllersó é executado se o modelo for válido

Annotations: [Required], [StringLength(150, MinimumLength = 2)], [MaxLength], [MinLength], [Range(1, 2500)], [EmailAddress], todas com ErrorMessage.

Pegadinha do Acervo: [Required] em int AutorId nunca falha. Se o JSON não mandar o campo, o int vale 0 (não null). Quem barra é o Service, que não acha o autor 0. Para o [Required] funcionar, o tipo teria que ser int?.

Padronizando o erro (ErroResponseDTO)

O InvalidModelStateResponseFactory no Program.cs troca a resposta padrão de validação por um ErroResponseDTO com Status 400, Mensagem "Um ou mais campos são inválidos." e um dicionário Erros (campo → mensagens).

Regra de negócio no Service, status no Controller

// Service: lança a exceção
if (existe) throw new InvalidOperationException("Já existe um livro com este título e autor.");

// Controller: traduz para HTTP
catch (InvalidOperationException ex) { return Conflict(new ErroResponseDTO { ... }); }  // slide: 409

No código do Acervo, o catch devolve BadRequest (400). E o ArgumentException ("Ao menos uma Categoria não existe.") não é capturado: vira 500.

7. Autenticação, autorização e JWT

Autenticação"Quem é você?" Login → credencial → verificação → usuário autenticado. Falhou: 401 Unauthorized.
Autorização"O que você pode fazer?" Ex.: usuário comum lista livros; só administrador apaga. Sem permissão: 403 Forbidden.
Autenticação tradicional (sessão)Token (JWT)
Cliente → usuário + senha → servidor valida → guarda uma sessão no servidorLogin → API valida → emite um token, que o cliente manda em cada requisição
Servidor guarda estadoStateless: combina com REST

Token: informação emitida após uma autenticação bem-sucedida e usada depois para identificar e autorizar o cliente.

JWT (JSON Web Token): formato compacto para transportar informações entre partes de forma verificável. Três partes separadas por ponto: header.payload.signature.

Header
Informações sobre o token: tipo (typ: JWT) e algoritmo de assinatura (alg: HS256).
Payload
Os claims: informações do usuário ou do token (sub, nome, email, role, exp). É codificado em Base64Url, não criptografado: qualquer um consegue ler. Nunca coloque senha.
Signature
Header + Payload + chave secreta. Verifica se o token foi alterado. Token alterado → 401.
Expiração
O token não deve valer para sempre (exp). Expirado → 401. Reduz o risco se ele vazar.
Authorization: Bearer eyJhbGciOi...
└─ header ───┘ └ tipo ┘ └ credencial (o token)

Endpoint público x protegido: GET pode ser público; POST pode exigir autenticação; DELETE pode exigir administrador. No ASP.NET: [Authorize], [Authorize(Roles = "Administrador")], [AllowAnonymous]; no Program.cs, AddAuthentication().AddJwtBearer(...) e app.UseAuthentication() antes de app.UseAuthorization().

8. Front-end em Angular consumindo a API

Está nos objetivos da matéria e no fluxo do projeto (API REST → banco → autenticação → aplicação Angular → integração), mas não apareceu nos slides que você mandou. Para as questões de concurso, o essencial:

  • Componente: classe TypeScript + template HTML + estilo. Service: classe @Injectable que concentra as chamadas à API, injetada nos componentes.
  • HttpClient: this.http.get<Livro[]>('https://localhost:7010/api/livros') retorna um Observable; a requisição só sai quando alguém faz .subscribe().
  • Data binding: {{ valor }} interpolação · [prop] property binding · (click) event binding · [(ngModel)] two-way.
  • CORS: o Angular roda em outra origem (ex.: localhost:4200), então a API precisa liberar essa origem (AddCors + UseCors). Sem isso, o navegador bloqueia a resposta.
  • JWT no front: guarda o token após o login e envia no cabeçalho Authorization: Bearer, normalmente com um interceptor.

Pegadinhas de prova

  • PUT substitui tudo (e pode criar); PATCH atualiza parte.
  • GET, PUT e DELETE são idempotentes; POST não.
  • 401 = não sei quem você é (ou token inválido/expirado). 403 = sei quem é, mas não pode.
  • Filtro sem resultado = 200 com []. Recurso por id inexistente = 404.
  • POST criado com sucesso = 201 Created (CreatedAtAction), não 200.
  • DELETE e PUT sem corpo de resposta = 204 No Content.
  • SOAP é protocolo e usa só XML; REST é estilo arquitetural e aceita JSON, XML etc.
  • Todo WebService precisa de rede; uma API não necessariamente.
  • Stateless: o servidor não guarda estado entre requisições. Código sob demanda é a única restrição REST opcional.
  • Payload do JWT é só codificado (Base64Url), não criptografado. A assinatura garante integridade, não sigilo.
  • Entity = persistência; DTO = transferência.
  • Controller não tem regra de negócio; o Service tem.
  • [ApiController] devolve 400 antes do método do controller rodar.
  • [Required] em int não funciona: o padrão é 0.
  • AsQueryable + Where não executam nada; só o ToListAsync() vai ao banco.
  • Sem SaveChangesAsync(), nada é gravado.
  • Add-Migration cria; Update-Database aplica.
  • AddScoped = uma instância por requisição.
