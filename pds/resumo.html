Processo de Desenvolvimento de Software · Prof. Alisson Kuhn

Resumo de prova

Processo bom gera software bom. Do cascata ao DevOps, a ideia é entregar com qualidade, mais rápido e com menos risco.

1. Engenharia de software e processo

  • Eng. de Software (IEEE): aplicação de uma abordagem sistemática, disciplinada e quantificável ao desenvolvimento, operação e manutenção.
  • Qualidade (Pressman): conformidade a requisitos funcionais e de desempenho, a padrões documentados e a características implícitas esperadas. Falta de requisito atendido = falta de qualidade. Qualidade não se coloca depois, vem do processo.
  • Processo de software: conjunto de atividades, métodos, práticas e tecnologia. Define quem faz o quê, quando e como.
  • Eng. de Software = qualidade + processo + métodos + ferramentas. Métodos = como fazer. Ferramentas = apoio (CASE). Procedimentos = elo entre métodos e ferramentas.
  • Fases genéricas: Definição (o quê), Construção (o como: projeto, código, testes), Manutenção.
  • 4 manutenções: corretiva (defeitos), adaptativa (novo ambiente/lei), perfectiva (novas funções), preventiva (facilitar o futuro).
  • ISO/IEC 12207: norma de ciclo de vida, 3 grupos de processos: fundamentais (aquisição, fornecimento, desenvolvimento, operação, manutenção), de apoio (documentação, qualidade, verificação, validação...) e organizacionais (gerência, melhoria, infraestrutura, treinamento). Não diz como fazer nem impõe modelo de ciclo de vida.
  • Maturidade: CMMI-Dev, PSP, MPS.Br.
No projeto: o pipeline (Trello, PR, CI, CD) é o nosso processo definindo quem faz o quê e em que ordem.

2. Modelos de processo (clássicos)

ModeloIdeiaProblema / quando usar
CascataSequencial linear: sistema, requisitos, projeto, código, testes, manutenção. Saída de uma fase é entrada da outra.Requisitos raramente são todos conhecidos no início; cliente só vê software no fim.
PrototipaçãoProtótipo para entender requisitos; refina até o cliente aprovar. Depois o protótipo é descartado.Cliente quer usar o protótipo como produto final; qualidade comprometida.
RADCiclo curtíssimo (60 a 90 dias), componentes reutilizáveis, equipes por módulo. Fases: modelagem do negócio, dos dados, do processo, geração da aplicação, teste.Exige requisitos bem entendidos, escopo restrito e sistema modularizável.
IncrementalCascata repetido + filosofia iterativa. Versão inicial é o núcleo; novas funções entram em incrementos.Bom quando é difícil detalhar tudo antes; ideal para sistemas pequenos.
EspiralCascata + prototipação + análise de risco. Ciclo: planejamento, análise de riscos, construção, avaliação do cliente.Realista para sistemas grandes; exige experiência em riscos.
4GLEspecifica em alto nível e o código é gerado automaticamente.Ferramentas de 4ª geração.

Evolutivos (incremental, espiral) são iterativos: versões cada vez mais completas. A escolha do modelo depende da natureza do projeto, dos métodos/ferramentas e dos produtos a entregar.

No projeto: usamos incremental e ágil: 2 sprints, cada uma entrega uma parte funcionando (Sprint 1 a base e o CRUD, Sprint 2 presença, histórico e deploy).

3. Metodologias ágeis

  • Por que surgiram: os modelos tradicionais têm muita documentação, iterações longas e pouca participação do cliente, o que gera retrabalho.
  • Manifesto Ágil (2001, Kent Beck e outros 16): 4 valores:
    • Indivíduos e interações mais que processos e ferramentas
    • Software funcionando mais que documentação abrangente
    • Colaboração do cliente mais que negociação de contratos
    • Responder a mudanças mais que seguir um plano
  • 12 princípios, os principais: satisfazer o cliente com entrega contínua; aceitar mudanças até no fim; entregar software funcionando com frequência (semanas); negócio e devs juntos todo dia; software funcionando é a medida de progresso; simplicidade; times auto-organizáveis; reflexão regular para melhorar.
  • Indicado quando: muita mudança, equipe pequena, prazo curto, desenvolvimento rápido é fundamental.
  • Exemplos: XP, Scrum, Kanban, Crystal, FDD, DSDM, TDD, BDD, DevOps, Lean.

5. Histórias de usuário

  • Técnica de requisitos ágil que captura quem, o quê e por quê, de forma curta (cabe num cartão). Nasceu no XP.
  • Formato: Como [papel], quero [ação], para que [benefício].
  • Escritas pelo cliente/negócio; o gerente de produto garante que sejam capturadas. Devs podem escrever as de requisitos não funcionais (segurança, desempenho).
No projeto (US02): "Como professor, quero marcar presente ou ausente cada aluno em uma data de aula, para controlar a frequência da turma." Com critérios de aceite (data padrão hoje, sem duplicar aluno na mesma data, confirmação ao salvar).

6. DevOps

  • Definição: cultura que aproxima Dev (desenvolvimento) e Ops (operação: sysadmin, DBA, redes, segurança), com práticas e ferramentas para entregar em alta velocidade e automatizar integração, teste, liberação e infraestrutura.
  • Problemas que resolve: lentidão, gargalos, defeitos, mudança de escopo, prazo e custo.
  • Benefícios: velocidade, entrega rápida, confiabilidade, escala, colaboração, segurança.
  • 4 pilares: Comunicação, Colaboração, Automação (o coração do DevOps) e Monitoração.
  • 8 etapas: Plan, Code, Build, Test, Release, Deploy, Operate, Monitor.
  • Componentes do pipeline: Continuous Delivery, Deployment, Testing, Operations, Monitoring e Feedback.

CI x Entrega x Implantação (cai muito)

PráticaO que faz
CI Integração ContínuaIntegra mudanças com frequência no código principal, com build e testes automáticos (unidade e integração).
Continuous Delivery Entrega ContínuaComplementa a CI: deixa o código sempre pronto para produção, com testes de aceitação em pré-produção. A ida à produção depende de aprovação manual.
Continuous Deployment Implantação ContínuaTudo automático até o usuário final, sem intervenção manual. Depende muito de testes automatizados bons.

Ferramentas citadas

Plan: Jira (e Trello). Code: Git/GitHub (repositório, branches, commits, pull requests, issues). Build/CI: Jenkins (e GitHub Actions). Test: Selenium. Release/Deploy/Operate: Docker (containers empacotam app + dependências) e Kubernetes (orquestra containers). Monitor: Nagios.

No projeto: Trello (Plan), GitHub + PR (Code), GitHub Actions CI com 11 etapas e PHPUnit (Build/Test), Docker/Compose + imagem no GHCR (Release), CD por SSH na VPS (Deploy), Nginx/HTTPS (Operate), /health + Netdata + fail2ban (Monitor). Como o CD é automático após o CI, é "implantação contínua", mas com uma trava de liberação.

7. UML e diagramas

  • UML: linguagem padrão para especificar, visualizar, construir e documentar sistemas. Não é processo nem metodologia. Padrão OMG desde 1997 (Booch e Rumbaugh). Versão 2.5.
  • Estruturais (o que o sistema é): classes, objetos, componentes, implantação, pacotes, estrutura composta, perfil.
  • Comportamentais (o que o sistema faz): casos de uso, atividades, máquina de estados e os de interação (sequência, comunicação, tempo, visão geral).
  • Análise: casos de uso, diagrama de atividades, modelo conceitual. Projeto: interação, classes, pacotes, mapeamento objeto-relacional.

Diagrama de Atividades

Fluxo de atividades de um processo (lógica de procedimento, fluxo de trabalho, processo de negócio). Atividades ligadas por transições. Foca no fluxo de atividade para atividade. Mapeamento de processos também usa fluxograma, BPMN (raias/swimlanes) e SIPOC (fornecedor, entrada, processo, saída, cliente).

Diagramas de Interação

  • Sequência: ênfase na ordem temporal das mensagens entre objetos. Elementos: linha de vida, barra de ativação, mensagem (vira método do objeto que recebe), retorno tracejado, mensagem para si mesmo (reflexão), loop (iteração), guarda (condicional).
  • Comunicação: ênfase na organização estrutural dos objetos.
  • Dependem de casos de uso e do modelo conceitual já prontos.
  • Polimorfismo: subclasses respondem à mesma operação (mesma assinatura) com comportamentos diferentes.
No projeto: um diagrama de sequência de "registrar presença": Professor, tela, controlador, banco (grava e atualiza se já existir para a data).

Pegadinhas de prova

  • Cascata: cliente só vê o software no fim. Prototipação: o protótipo é descartado.
  • Espiral = o único com análise de risco explícita.
  • RAD exige modularização e requisitos claros.
  • Delivery tem aprovação manual; Deployment é 100% automático.
  • Scrum: o PO prioriza o backlog; o Scrum Master é coach, não chefe.
  • Automação é o "coração" do DevOps; DevOps é cultura, não só ferramenta.
  • UML não é metodologia; a ISO 12207 não diz como fazer.
  • Manifesto ágil: "mais que", não "no lugar de". Os itens da direita ainda têm valor.
